# Code Review — v1 (2021) → v2 (2026)

Revisão completa do código original do desafio (commit `f498edb`, Angular 11 + Ionic 5 + AngularFire 6) e do que foi feito na modernização. Os problemas estão ordenados por severidade dentro de cada área.

**Legenda:** 🔴 crítico · 🟠 alto · 🟡 médio · 🔵 baixo

---

## 1. Segurança

| #   | Sev. | Problema na v1                                                                                                                                                                                                                                                      | Correção na v2                                                                                                                                                                                                                                 |
| --- | ---- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| S1  | 🔴   | **Autorização só visual.** A rota `/admin` não tinha guard: o link sumia do menu para estoquistas, mas bastava digitar a URL. Também não havia regras do Firestore versionadas no repositório, então não era possível auditar quem podia gravar o quê.              | Guards funcionais (`authGuard`, `guestGuard`, `adminGuard`) e, principalmente, [`firestore.rules`](../firestore.rules) versionado: apenas `adm` cria/renomeia/remove produtos; estoquista só altera `qtd` e nunca para negativo.               |
| S2  | 🔴   | **Escalonamento de privilégio por design.** `AuthService.newUser()` gravava `nome` e `categoria` em `users/{uid}` a partir do cliente — se funcionasse, qualquer usuário poderia se promover a `adm`. (Na prática quebrava por um bug: `user.Ref` era `undefined`.) | O perfil passou a ser **somente leitura** no cliente (`allow write: if false`). A categoria é definida fora do app (console/Admin SDK).                                                                                                        |
| S3  | 🟠   | **Enumeração de contas.** O login exibia “Senha Incorreta” ou “E-mail não encontrado”, revelando quais e-mails têm cadastro.                                                                                                                                        | [`auth-error.mapper.ts`](../src/app/core/utils/auth-error.mapper.ts) retorna a mesma mensagem (“E-mail ou senha inválidos.”) para ambos os casos — coberto por teste.                                                                          |
| S4  | 🟠   | **Histórico adulterável.** Não havia regra impedindo editar ou apagar registros de `history`, que deveria ser a trilha de auditoria.                                                                                                                                | `history` é _append-only_: criação exige `uid == request.auth.uid`; `update`/`delete` negados; o registro precisa bater com o saldo do produto antes (`get`) e depois (`getAfter`) da transação, impedindo movimentações forjadas.             |
| S5  | 🟡   | Sem cabeçalhos de segurança no Hosting.                                                                                                                                                                                                                             | [`firebase.json`](../firebase.json) com CSP restritiva, `X-Frame-Options`, `X-Content-Type-Options`, `Referrer-Policy`, `Permissions-Policy` e HSTS. Build sem `inlineCritical` para não precisar de `unsafe-inline` em scripts.               |
| S6  | 🟡   | Dependências fora de suporte: Angular 11 (EOL em 2022), Firebase 8, TypeScript 4.0, Protractor (descontinuado). Desde 2022 o `sweetalert2` passou a incluir _protestware_ (comportamento oculto em domínios `.ru`/`.by`).                                           | Angular 22, Ionic 9, Firebase 12, TS 6. SweetAlert2 substituído pelos overlays nativos do Ionic. `npm audit`: **0 vulnerabilidades** (`@grpc/grpc-js` transitivo fixado via `overrides`). Dependabot + CodeQL no CI.                           |
| S7  | 🔵   | Chave do Firebase tratada como segredo implícito, `environment.ts` com `production: true`.                                                                                                                                                                          | Documentado que a config web do Firebase é pública por natureza — a proteção real está nas regras e nas restrições de domínio da API key. Credenciais do modo demo só entram no bundle `demo` (token `DEMO_LOGIN_HINT`), nunca no de produção. |

## 2. Corretude / bugs

| #   | Sev. | Problema na v1                                                                                                                                                                                                                                                 | Correção na v2                                                                                                                                                      |
| --- | ---- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| B1  | 🔴   | **Condição de corrida no estoque.** Entrada/saída calculava o novo saldo com o valor _da tela_ e gravava `products` e `history` em duas operações separadas. Dois estoquistas simultâneos = saldo errado; falha no meio = histórico sem baixa (ou vice-versa). | `StockMovementRepository.register()` usa `runTransaction`: lê o saldo atual no servidor, aplica a regra (`applyMovement`) e grava produto + histórico atomicamente. |
| B2  | 🟠   | Validação de quantidade frágil: `parseInt('12abc') === 12`, entrada de `0` aceita, mesma checagem duplicada (`qtdR < 0` duas vezes).                                                                                                                           | `parseQuantity()` aceita apenas inteiros positivos (regex + `Number.isSafeInteger`), validada na UI, no service e de novo na regra de domínio e no Firestore.       |
| B3  | 🟠   | `login()` sempre falhava após autenticar: `newUser()` acessava `user.Ref.set` (inexistente).                                                                                                                                                                   | Login não grava nada; apenas autentica e carrega o perfil.                                                                                                          |
| B4  | 🟡   | Edição no admin usava uma flag **global** (`editar`): ao clicar “Editar” todas as linhas viravam inputs, e o `ngModel` mutava o objeto antes de confirmar.                                                                                                     | Estado de edição por linha (`signal<EditState>`), com rascunho separado, “Salvar”/“Cancelar”, Enter/Esc.                                                            |
| B5  | 🟡   | `AppComponent` redirecionava para `/home` a cada evento de auth — recarregar `/product` sempre jogava o usuário para a home.                                                                                                                                   | Navegação decidida por guards; a URL atual é preservada no reload.                                                                                                  |
| B10 | 🟡   | _(encontrado no CR da v2)_ No logout, o listener do perfil `users/{uid}` pode receber `permission-denied` antes do `onAuthStateChanged(null)`; o erro encerrava o stream da sessão e o app quebrava até recarregar.                                            | `catchError` no listener do perfil com _fallback_ de menor privilégio.                                                                                              |
| B6  | 🟡   | `ProductPage` fazia `user.uid` dentro de `onAuthStateChanged` sem checar `null` (erro após logout) e nunca cancelava a inscrição (vazamento).                                                                                                                  | Sessão exposta como `signal` em um `AuthService` raiz; streams convertidos com `toSignal` (unsubscribe automático).                                                 |
| B7  | 🟡   | IDs gerados com `new Date().getTime()` — colisão quando duas gravações ocorrem no mesmo milissegundo.                                                                                                                                                          | IDs automáticos do Firestore / `crypto.randomUUID()`.                                                                                                               |
| B8  | 🔵   | `ProdutosService.updateQtd()` na verdade atualizava o **nome**; `pegaIdUsuario(): void` “retornava” dentro de um callback.                                                                                                                                     | Métodos com nomes fiéis (`rename`, `registerEntry`, `registerExit`) e tipos explícitos.                                                                             |
| B9  | 🔵   | `menu-routing.module.ts` declarava rotas com `component: ProductPageRoutingModule` (um módulo no lugar de componente), e o `MenuPageModule` era importado em todas as páginas, duplicando rotas.                                                               | Rotas centralizadas em `app.routes.ts`, com layout (`ShellComponent`) + rotas filhas lazy.                                                                          |

## Pendências recomendadas (fora do escopo do código)

- **Publicar as regras** no projeto do Firestore: `firebase deploy --only firestore:rules --project mm12desafio`.
- **Restringir a API key** do Firebase aos domínios do Hosting no Google Cloud Console e habilitar **App Check**.
- **Definir perfis via Custom Claims** (Admin SDK) em vez de leitura do documento `users/{uid}` nas regras — elimina um `get()` por requisição.
- O estoquista ainda consegue alterar `qtd` sem gravar histórico (as regras não sabem o ID do registro criado no mesmo lote). Para fechar isso, mover as movimentações para uma **Cloud Function** (callable) e negar escrita direta em `qtd`.
- Testes das regras com o **Firebase Emulator** (`@firebase/rules-unit-testing`) — requer JDK 21 no ambiente.
